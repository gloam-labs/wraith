    Wraith — API Reference - v1.0.0

    Wraith 👻

    Soroban incoming token transfer indexer — fills the gap that Horizon leaves open.

    Horizon indexes Classic Stellar operations (payments, path payments) but does not index Soroban transfer events by recipient address. Wraith polls Stellar RPC getEvents, parses CAP-67/SEP-41 token events (transfer, mint, burn, clawback), stores them in Postgres, and exposes a REST API to query by address.

    How It Works

    flowchart TD
    SN["☆ Stellar Network\n(Soroban ledgers, ~5 s each)"]
    RPC["Soroban RPC\ngetEvents"]
    SAFE["fetchEventsSafe\nrpc.ts"]
    BISECT{{"XDR decode\nerror?"}}
    SKIP["Skip bad ledger\nlog warning & advance"]
    DECODE["parseEvents\nSEP-41 / CAP-67 normalisation\nScVal → JS native\ndecoder.ts"]
    DB[("Postgres\nTokenTransfer table\nupsert on eventId\nPrisma — db.ts")]
    STATE["IndexerState row\nlastIndexedLedger"]
    HTTP["Express REST API\napi.ts"]
    WS["WebSocket stream\n/subscribe/:address\nws.ts"]
    C1["REST Clients\ncurl · SDK · dApp"]
    C2["Real-time Clients\nbrowser · bot"]

    SN -->|ledger stream| RPC
    RPC -->|raw contract events| SAFE
    SAFE --> BISECT
    BISECT -- yes --> SKIP
    BISECT -- no --> DECODE
    SKIP -->|advance cursor| STATE
    DECODE -->|TransferRecord batch| DB
    DB --> STATE
    DB --> HTTP
    DB --> WS
    HTTP --> C1
    WS --> C2

    startIndexer() runs an infinite loop, calling getLatestLedger() every POLL_INTERVAL_MS (default 6 s, ≈ 1 ledger). Each cycle calls fetchEventsSafe, which requests a batch of Soroban contract events from the RPC via getEvents. parseEvents then decodes each raw ScVal topic/value pair into a typed TransferRecord covering transfer, mint, burn, and clawback event types as defined by SEP-41 / CAP-67. upsertTransfers bulk-inserts the records via Prisma using skipDuplicates: true on eventId, making re-indexing overlapping ledger ranges idempotent. The Express REST API and WebSocket server both read exclusively from Postgres, keeping the ingestion and query paths fully independent.

    Note

    Bisection strategy for Protocol 22 XDR errors — Stellar protocol upgrades occasionally introduce new XDR types that older SDK versions cannot decode (e.g. ScAddressType value 3 added in Protocol 22). When fetchEventsSafe encounters an XDR decode error on a multi-ledger batch, it bisects the ledger range recursively — splitting it into two halves and retrying each — until it isolates the single problematic ledger. That ledger is then skipped with a warning log, and indexing continues from the next ledger. This ensures one bad ledger cannot stall the entire indexer.

    Quick Start

    1. Clone & install

    git clone <repo>
    cd wraith
    npm install
    npx prisma generate

    2. Configure

    cp .env.example .env

    Testnet setup (quick start):

    DATABASE_URL="postgresql://wraith:wraith@localhost:5432/wraith"
DIRECT_DATABASE_URL="postgresql://wraith:wraith@localhost:5432/wraith"
STELLAR_NETWORK="testnet"
# SOROBAN_RPC_URL_TESTNET (or legacy SOROBAN_RPC_URL) is optional on testnet —
# the default public endpoint (https://soroban-testnet.stellar.org) is used automatically
SOROBAN_RPC_URL_TESTNET=

START_LEDGER=
SAC_CONTRACT_IDS=
PORT=3000

    Mainnet setup (production):

    DATABASE_URL="postgresql://wraith:wraith@localhost:5432/wraith"
DIRECT_DATABASE_URL="postgresql://wraith:wraith@localhost:5432/wraith"
STELLAR_NETWORK="mainnet"
# Required on mainnet — no free public Soroban RPC exists:
# In multi-network setups (`NETWORKS=testnet,mainnet`), set SOROBAN_RPC_URL_MAINNET.
# In single-network deployments (`STELLAR_NETWORK=mainnet`), SOROBAN_RPC_URL may also be used.
SOROBAN_RPC_URL_MAINNET="https://mainnet.stellar.validationcloud.io/v1/"

# Strongly recommended on mainnet: filter to specific contracts to reduce load
SAC_CONTRACT_IDS="CTOKEN1...,CTOKEN2..."
START_LEDGER=
PORT=3000

    Tip: In multi-network mode (NETWORKS=testnet,mainnet), SOROBAN_RPC_URL_MAINNET is required to index mainnet. If omitted, the mainnet indexer will not start and mainnet reads will be marked stale with an explicit staleness indicator (stale: true, indexer_running: false, header X-Data-Stale: true). Single-network deployments may still use SOROBAN_RPC_URL with STELLAR_NETWORK=mainnet.

    3. Start Postgres

    docker compose up -d db

    4. Create the schema

    npm run db:push

    This is the same guarded convergence the service runs on startup. The committed migrations under prisma/migrations/ are a change history, not an init script, and are not applied by startup — see docs/drift-recovery.md for why, with the evidence.

    5. Seed the database (optional)

    Populate the database with deterministic test data for development and testing:

    npm run db:seed

    By default, this seeds testnet. To seed mainnet:

    npm run db:seed -- --network=mainnet

    6. Rebuild account summaries (maintenance)

    AccountSummary is maintained incrementally during indexing, but can be repaired per network from TokenTransfer with:

    npm run backfill:summaries -- --network testnet

    Flags:

    • --network <testnet|mainnet> (required) — rebuilds only the named network; the other network's rows are untouched.
    • --dry-run — scans transfers and prints how many summary rows would be inserted, updated, or deleted without writing anything.
    • --accept-truncated-history — required if older transfers for that network have already been pruned by RETENTION_DAYS (when the oldest stored transfer is newer than the oldest summary, or no transfers remain while summaries exist); without this flag the command refuses to shrink lifetime totals.
    • --batch-size <num> — rows per keyset page (overrides BACKFILL_BATCH_SIZE, default 5000).

    The command pages TokenTransfer by keyset (id) and applies only the computed diff inside one transaction, so API readers never observe an empty AccountSummary table during a rebuild. Note that if retention pruning has already deleted older transfers, a rebuild can only recompute totals from the transfers still stored in Postgres unless --accept-truncated-history is passed explicitly.

    API Reference

    Base URL: http://localhost:3000

    Offramp order lookups need a bearer token; see docs/offramp-orders.md.

    GET /transfers.csv and /transfers.parquet need no filter, and are capped rather than rejected: a request with nothing narrowing it returns the first maxRows rows instead of the whole table. When rows were left behind, the response says so in X-Truncated: true and X-Row-Limit: <n>, set before the body starts — so a client can tell a complete export from a partial one without counting. Narrow with address, contractId, fromLedger/toLedger or fromDate/toDate, or raise maxRows up to 500 000.

    CORS

    The read API answers every origin: Access-Control-Allow-Origin: *. That is deliberate — the data is public chain data, and a browser dashboard on any domain is the intended consumer. The same is true of GraphQL (read-only schema), the fee quote and the offramp quotes.

    The surfaces that are not public are restricted to the origins in CORS_ALLOWED_ORIGINS — a comma-separated list, matched exactly:

    Surface Routes
    Offramp /offramp/orders*, /offramp/verify-bank, /offramp/trustline
    Naira rails /ngn/*
    Webhook subscriptions /webhooks
    Metrics /metrics
    Any other write a route nobody has classified yet

    A request from an origin that is not on that list is refused with 403 and the code origin_not_allowed, before the route runs — so a page on any site cannot create an offramp order. A request with no Origin header is always served: the mobile app, a server-to-server caller and curl all send none, and CORS has nothing to say about them.

    POST /webhooks/linq is the payout provider calling us. It is authenticated by an HMAC signature over the raw body, it gets no CORS headers at all, and it is never refused by the origin policy — a payment rail must not stop working because the list changed.

    src/middleware/cors.ts holds the whole table and the reasoning behind each row.

    Selecting a network

    Wraith stores testnet and mainnet rows in the same tables, discriminated by a network column, and a single process can index both (NETWORKS=testnet,mainnet). Every read route accepts a selector so a caller can say which one it wants:

    # query parameter
    curl "http://localhost:3000/transfers/incoming/GABC…?network=mainnet"

    # or a header — the query parameter wins if both are present
    curl -H "X-Network: mainnet" http://localhost:3000/transfers/incoming/GABC…

    Omit it and you get the deployment's configured network (STELLAR_NETWORK, defaulting to testnet) — the behaviour every route had before the selector existed, so nothing changes for existing callers.

    Two kinds of rejection, both 400, because they need different fixes:

    Request Response
    ?network=mainet Invalid network: "mainet". Valid values: testnet, mainnet.
    ?network=mainnet on a testnet-only deployment Network "mainnet" is not enabled on this deployment. Enabled networks: testnet.

    An un-indexed network is refused rather than answered with an empty list: "no transfers" and "this process has never looked at that chain" are different statements, and returning [] for both is how a dashboard ends up confidently showing zero.

    GraphQL takes the same ?network= / X-Network selector, and each field also accepts a network: argument that overrides it — so one document can read both chains in a single round-trip:

    {
  testnet: transfers(address: "GABC…", network: TESTNET, includeTotal: true) { total hasMore }
  mainnet: transfers(address: "GABC…", network: MAINNET, includeTotal: true) { total hasMore }
}

    transfers accepts the same filters as the REST transfer routes, with the same validation — limit must be 1–200, fromLedger/toLedger are inclusive ledger bounds, fromDate/toDate are ISO 8601 datetimes with an offset, eventTypes is a list of transfer, mint, burn or clawback (case-insensitive), and token filters to one token contract like contractId does. Transfer carries the id REST already returns, and TokenSummary carries displayTotalReceived, displayTotalSent and displayNetFlow — the raw totals scaled by the token's decimals, as GET /summary/:address computes them.

    {
  transfers(address: "GABC…", limit: 2, eventTypes: ["transfer"], fromLedger: 1000) {
    transfers { id eventId amount displayAmount }
    nextCursor
    hasMore
  }
}

    Page with the cursor, not the offset: pass the previous page's nextCursor back as cursor to continue. A malformed cursor is an error, not a silent first page — the list would otherwise restart from the top and loop forever. cursor and offset do not combine; when a cursor is given, the offset is ignored, exactly as on REST.

    WebSockets take it on the upgrade URL — ws://host/subscribe/GABC…?network=mainnet — and the stream is filtered to that network. A socket opened with an invalid or un-enabled selector is closed with code 1008 and the reason, rather than left open delivering nothing. GraphQL subscriptions work the same way on /graphql/subscriptions, with an optional per-subscription network: argument.

    GET /status

    Indexer health — current ledger, network tip, lag, uptime.

    curl http://localhost:3000/status

    {
      "ok": true,

    last_indexed_ledger is a snake_case alias of lastIndexedLedger — the same name the Prometheus gauge is exported under. Both always carry the same value.

    GET /metrics

    Indexer and process metrics in Prometheus text exposition format, for scraping, dashboards, and alerting.

    curl http://localhost:3000/metrics

    # HELP ledgers_indexed_total Ledgers advanced through by the indexer, per network
    # TYPE ledgers_indexed_total counter
    ledgers_indexed_total{network="mainnet"} 48213
    # HELP last_indexed_ledger Highest ledger sequence committed by the indexer, per network
    # TYPE last_indexed_ledger gauge
    last_indexed_ledger{network="mainnet"} 5842100
    # HELP transfers_stored_total Rows persisted by the indexer, per network and record type (fungible, nft, lp, host_fn)
    # TYPE transfers_stored_total counter
    transfers_stored_total{network="mainnet",type="fungible"} 182400
    transfers_stored_total{network="mainnet",type="nft"} 310
    transfers_stored_total{network="mainnet",type="lp"} 92
    transfers_stored_total{network="mainnet",type="host_fn"} 182802
    # HELP events_skipped_total Events dropped during ingest, by network and reason
    # TYPE events_skipped_total counter
    events_skipped_total{network="mainnet",reason="unrecognised"} 94100
    events_skipped_total{network="mainnet",reason="malformed"} 0
    Metric Type Labels What it says
    ledgers_indexed_total counter network Ledgers the indexer has advanced through. A flat rate() on a network whose loop should be running means it has stalled.
    transfers_stored_total counter network, type Rows persisted, split fungible / nft / lp / host_fn — each comes off a distinct parse path and one can break while the others keep working. host_fn is the table that once grew to 1 776 MB; its write rate is the number an operator most needs to watch.
    rpc_errors_total counter outcome Failed RPC attempts. retry counts attempts withRetry absorbed, exhausted counts calls that gave up — a degrading endpoint shows up in retry long before it fails a call.
    events_skipped_total counter network, reason Events dropped during ingest. unrecognised is non-token events (normal background noise); malformed is a fungible token event whose structure was invalid; nft_parse is an NFT event parseNftTransferEvent returned null for; host_fn is a host-function log event that threw during parse. All carry network so a rising count can be pinned to a chain in a process running multiple networks.
    last_indexed_ledger gauge network Highest committed ledger. Against the chain tip, this is lag.
    db_query_duration_seconds histogram operation Duration of instrumented DB operations, failures included.
    http_requests_total counter method, route, status HTTP requests served. route is the full Express route pattern (e.g. /search, /offramp/rate, /accounts/:address/transfers), never the raw URL, so addresses and dynamic parameters never become label values; an unmatched request reports route="unknown".
    http_request_duration_seconds histogram method, route HTTP latency, 5 ms to 40 s. Labeled by method and full route pattern. No status label — the split is rarely worth the extra series.
    provider_request_duration_seconds histogram provider, operation, outcome Time inside a payment-provider call (Linq), separately from the request. Same unit and buckets as the HTTP histogram: http_request_duration_seconds - provider_request_duration_seconds is wraith's own time. operation is a fixed list (offramp_order, bill_pay, …), never a URL.

    Standard process_* and nodejs_* metrics are exported alongside these.

    The endpoint reads in-process counters only — no DB, no RPC — so it keeps answering while the subsystems it reports on are down, and it is exempt from the API rate limit so scrapes do not go dark under load.

    GET /transfers/incoming/:address

    All token transfers received by an address.

    Param Type Description
    network string testnet or mainnet (see above)
    contractId string Filter to a specific token contract (C...)
    token string Filter to a specific token contract (C...); the same filter as contractId, and it wins if both are sent
    fromLedger int Inclusive lower ledger bound
    toLedger int Inclusive upper ledger bound
    fromDate string ISO 8601 inclusive lower bound on ledgerClosedAt
    toDate string ISO 8601 inclusive upper bound on ledgerClosedAt
    eventType string Comma-separated event types: transfer, mint, burn, clawback
    limit int Page size (1–200, default 50)
    offset int Pagination offset (default 0)
    cursor string Opaque pagination cursor; continue from nextCursor
    includeTotal bool Also return an exact total. Runs a COUNT over every match, so it is markedly slower; omit it and use hasMore / nextCursor
    $filter string OData filter expression
    $select string Comma-separated field list to return

    The same parameters apply to GET /transfers/outgoing/:address and the combined GET /transfers/address/:address route, which adds a per-row direction.

    # All incoming transfers for an address
    curl "http://localhost:3000/transfers/incoming/GABC123..."

    # Filter to a specific token, last 1000 ledgers
    curl "http://localhost:3000/transfers/incoming/GABC123...?contractId=CTOKEN...&fromLedger=5840000&limit=20"

    cd clients/react-query && npm install && npm run generate   # regenerate the client types

    GET /candles/:bucket/:contractId

    Returns OHLC candles from the existing ohlc aggregate tables. bucket is 1m, 1h, or 1d; contractId is a 56-character Stellar contract address. Pagination uses limit (1–1000, default 100) and offset (non-negative, default 0). Refreshes are owned by the worker; there is no public refresh endpoint.

    The database must already contain working ohlc.candles_* tables and ohlc.refresh_candles_*() functions. They are not installed by Prisma's current startup path; the legacy sql/001_ohlc_aggregates.sql requires separate repair and deployment. These legacy aggregates do not separate networks, so they must not be used with a database containing transfers from multiple networks.

    The read route and scheduled refresh share one opt-in: set OHLC_REFRESH_INTERVAL_MS=60000 to enable both after those database prerequisites are met. Unset, invalid, or 0 disables both; SKIP_INDEXER=true also disables both. They require exactly one enabled network matching STELLAR_NETWORK (default testnet); multi-network configurations leave the route unmounted. The worker stops scheduling on shutdown and skips ticks while an earlier refresh is still running.

    Run npm run docs:openapi with the same environment as the deployment. Without the opt-in, the generated specification omits the candles route. For an enabled single-network deployment, generate it with OHLC_REFRESH_INTERVAL_MS=60000 npm run docs:openapi (and the deployment's network settings).

    RPC URL Resolution

    Wraith resolves the RPC endpoint per network:

    1. SOROBAN_RPC_URL_<NETWORK> (or STELLAR_RPC_URL_<NETWORK>) — explicit per-network variable (SOROBAN_RPC_URL_TESTNET, SOROBAN_RPC_URL_MAINNET). Always wins for that network.
    2. SOROBAN_RPC_URL / STELLAR_RPC_URL — legacy variable; honoured only for the configured network (STELLAR_NETWORK), preventing accidental cross-network configuration.
    3. testnet default → https://soroban-testnet.stellar.org (free public endpoint).
    4. mainnet default → error: requires explicit SOROBAN_RPC_URL_MAINNET (or SOROBAN_RPC_URL with STELLAR_NETWORK=mainnet). There is no free public mainnet Soroban RPC.
    5. If startAllIndexers encounters an unconfigured RPC for an enabled network (e.g. mainnet missing SOROBAN_RPC_URL_MAINNET), that network loop is marked not started, /status reports running: false with the exact error, and read endpoints for that network serve existing indexed data with explicit staleness markers (stale: true, indexer_running: false, X-Data-Stale: true).

    Indexer Source Fallback

    If HORIZON_URL is set, the indexer checks the RPC source first and switches to Horizon when the RPC health check fails. It switches back automatically once RPC becomes healthy again.

    Database Read Replicas

    Wraith supports distributing database read load across read replicas configured via DATABASE_REPLICAS (a comma-separated list of Postgres connection URLs).

    What Replicas Are Used For

    Replicas offload high-volume read traffic from the primary database for append-only, high-throughput indexed data where slight replication lag (eventual consistency) is acceptable:

    • Token Transfers (TokenTransfer)
    • NFT Transfers (NftTransfer)
    • Host Function Logs (HostFnLog)
    • LP-Share Transfers (LpShareTransfer)
    • Account Summaries (AccountSummary)

    What Replicas Are NEVER Used For

    Any table requiring read-after-write consistency or transactional integrity never routes reads to a replica; these queries always execute directly on the primary:

    • Order Processing & Balances: OfframpOrder, NgnOrder, FeePolicy, FeeQuote, MoneyFailure (ensures order creation, deduplication, and retry lookups immediately observe recent writes).
    • Indexer State & Cursors: IndexerState, IndexerCheckpoint, RetentionJobRun, ContractTombstone, BackfillCursor (prevents indexer startup loops from re-processing finished ledgers due to stale cursor reads).
    • Metadata Caches: TokenMetadata, NftMetadata (prevents redundant RPC fetches and cache thrashing following an initial cache miss write).
    • Webhooks: WebhookSubscription, WebhookDelivery.
    • Discord Authentication & Proofs: DiscordMember, DiscordLinkCode, DiscordGithubRequest.
    • Raw SQL Queries ($queryRaw, $executeRaw) & Interactive Transactions ($transaction): Always bypass replicas and execute on the primary.

    Forcing the Primary for a Read

    Callers can force a read to execute on the primary database for a specific operation:

    1. Via prisma.$primary: await prisma.$primary.tokenTransfer.findMany(...)
    2. Via withPrimary: await withPrimary(async () => prisma.tokenTransfer.findMany(...))
    3. Via query args: await prisma.tokenTransfer.findMany({ where: { ... }, forcePrimary: true })

    Health Checks and Failover

    • Replicas are probed every 10 seconds (or configured interval) using SELECT 1.
    • When a read on a replica fails with a connection or infrastructure error, that replica is immediately marked unhealthy and skipped on subsequent queries without waiting for the health check timer. The query transparently falls back to the primary.
    • Errors that are the query's own fault (e.g. invalid arguments, validation errors, schema constraint violations) do not trigger primary fallback and do not mark the replica unhealthy.

    Metrics

    Read routing and failovers are tracked in Prometheus metrics:

    • db_reads_total{target="primary|replica"}: Read queries executed against the primary vs. replicas.
    • db_read_fallbacks_total: Total number of queries that fell back from a replica to the primary after a connection error.

    Why Horizon Doesn't Cover This

    From the CAP-67 discussion, SDF's stated position:

    "We've made that mistake before with Horizon, by solving all indexing problems at the Horizon layer which encouraged folks to build on Horizon rather than innovate on new and or better data sources."

    Wraith is the third-party solution that SDF's architecture intentionally encourages.

    Command-Line Interface (CLI)

    Wraith includes a lightweight, powerful command-line interface shipped as @veil/wraith-cli. It allows developers to query transfer histories, get aggregate token summaries, and stream live Stellar Soroban events directly in their terminal without writing boilerplate.

    You can run it instantly without installation using npx:

    npx @veil/wraith-cli --help

    Configuration

    By default, the CLI connects to the public Wraith instance (https://api.wraith.veil.co). You can point it to a self-hosted instance or a local development server by setting the WRAITH_URL environment variable:

    export WRAITH_URL="http://localhost:3000"

    Commands & Examples

    1. Query transfers

    Retrieve transfer histories (transfers, mints, burns, clawbacks) for any Stellar address:

    # Get all transfers for a specific account (pretty ASCII table by default)
    npx @veil/wraith-cli transfers --account GABCDEFGHIJKLMNOPQRSTUVWXYZ

    # Filter transfers to a specific token contract
    npx @veil/wraith-cli transfers --account GABCDEFGHIJKLMNOPQRSTUVWXYZ --contract CB64D3G7SM2RTH6ISYIG4P2IYYD6J2OFR6B

    # Retrieve only incoming transfers with custom pagination and limit
    npx @veil/wraith-cli transfers --account GABCDEFGHIJKLMNOPQRSTUVWXYZ --direction incoming --limit 10 --offset 0

    # Emit parseable JSON for scripts or piping
    npx @veil/wraith-cli transfers --account GABCDEFGHIJKLMNOPQRSTUVWXYZ --json

    2. Account summaries

    Get a grouped summary of token balances, incoming/outgoing flows, and transaction counts:

    # View aggregate token statistics for an address
    npx @veil/wraith-cli summary GABCDEFGHIJKLMNOPQRSTUVWXYZ

    # Narrow down the summary to a specific timeframe
    npx @veil/wraith-cli summary GABCDEFGHIJKLMNOPQRSTUVWXYZ --from-date 2025-01-01T00:00:00Z --to-date 2025-01-31T23:59:59Z

    # Get raw JSON output
    npx @veil/wraith-cli summary GABCDEFGHIJKLMNOPQRSTUVWXYZ --json

    3. Live watch (Streaming)

    Establish a real-time WebSocket connection to stream new transfers as soon as they are indexed by the server:

    # Stream all incoming/outgoing transfers for a specific address in real time
    npx @veil/wraith-cli watch GABCDEFGHIJKLMNOPQRSTUVWXYZ

    # Stream live events filtered by a specific token contract
    npx @veil/wraith-cli watch GABCDEFGHIJKLMNOPQRSTUVWXYZ --contract CB64D3G7SM2RTH6ISYIG4P2IYYD6J2OFR6B

    # Output live streams as a sequence of raw JSON lines (perfect for logging/scripting)
    npx @veil/wraith-cli watch GABCDEFGHIJKLMNOPQRSTUVWXYZ --json

    4. Webhook Management

    Manage real-time webhook subscriptions:

    # List registered webhooks
    npx @veil/wraith-cli webhooks list

    # Register a new webhook url subscribing to specific events
    npx @veil/wraith-cli webhooks create https://your-app.com/webhook --events transfer,mint

    # Delete a webhook registration
    npx @veil/wraith-cli webhooks delete <webhook-id>
